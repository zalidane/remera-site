Summary

Remera helps you rate meals and scan restaurant menus using AI-powered nutrition guidance. Key points:

  • No account required. We do not ask you to create an account, sign in, or provide an email address to use the App.
  • Profile data stays on your device unless you use meal rating or menu analysis, which send health metrics (not your name) for objective AI analysis.
  • We do not sell your data and we do not use third-party advertising or analytics SDKs.
  • Menu photos are not uploaded. On iOS, the camera image is read on your device. Android does not capture a menu photo.
  • Payments stay with Apple. We do not receive or store your payment card details. The iOS app sends a StoreKit 2 purchase proof so our API can ask Apple whether Premium is active.

1.2 Information sent when you use App features

When you use certain features, the App sends data over the internet to our Service so we can generate results for you:

Feature Data sent Recipient
Meal rating Meal description you enter; relevant fields from your profile (age, gender, height, weight, activity level, goal, calorie targets). Your name is not sent. Our API server, which forwards content to OpenAI for AI analysis

The Android menu scanner does not capture a photo, does not run on-device OCR, and does not upload an image. Android meal rating can still send the meal description and profile fields above.

We do not store meal descriptions, menu text, photos, or profile fields in a database. Those requests are processed in memory and the result is returned. The Service does keep the usage counter and Premium entitlement cache described in Sections 1.3 and 1.5.

Both apps omit your name from the API payload. If a request still includes a name, the prompts do not use it.

1.3 Device identifier and usage limits

Free and Premium analyses share one daily cap. The App keeps a copy of the remaining count on the device so the screen can show it, and the API keeps the counter that actually enforces the cap.

Data Purpose Storage
Daily analysis count on the device Show how many analyses are left. Resets at midnight UTC. iOS: device Keychain. Android: encrypted local preferences.
Device identifier Key the server usage counter. A random id created on the device, not an advertising id (not IDFA or GAID). iOS: UserDefaults. Android: app preferences. Sent on AI requests as the X-Device-Id header.
Server daily usage counter Enforce the daily cap and the short cooldown between analyses. Not used for advertising or to build a profile. Redis key remera:usage: plus that device id. The value is the UTC day, the count, and the time of the last allowed request.

The server count resets when the UTC date changes. After each allowed analysis, that Redis key is set to expire one hour after the next UTC midnight (and at least one hour after the request). If a request has no device id, the API uses the request IP as the key instead.

Deleting your profile does not clear the device identifier or the on-device count, so the daily limit cannot be reset by deleting the profile. Deleting the App removes the on-device id and count. The server key expires on its own as described above.

We do not collect advertising identifiers and we do not use cross-app tracking for advertising.

If Redis is not configured, the API keeps the same counter in process memory until the process restarts. The deployed Service uses Redis.

1.4 Information collected automatically by our servers

When the App contacts our API, standard technical data is logged:

  • IP address, date and time, HTTP method, path, status code, and response size (HTTP access log)
  • User-Agent string (the App sends Remera/1.0)
  • A short usage line for each meal-rating or menu-analysis request: the tier that was applied, the daily limit, how many analyses remain, whether the app claimed Premium, whether a purchase proof was presented and which kind (none, signed transaction, transaction id, or both), the verification result, the App Store environment when known, the last four digits of Apple’s original transaction id when known, and a short reason code

Menu analysis also logs the character count and line count of the menu text. When it finishes, it logs those counts again, how many dishes were returned (best, recommended, and avoid), and how long the handler took.

We do not log the meal description, the menu text, profile fields, photos, dish names, reasons, scores, or the model’s response. A failed model call logs the error name and a status or code, not the model output. A failed subscription check logs a short reason and at most the last four digits of a transaction id. Long tokens are redacted. Server errors log the HTTP status, error name, and a short message; validation failures do not include the model output.

The signed App Store transaction and the full transaction id are not written to these logs.

Our API is hosted on Railway. Server logs are retained only as long as needed for security, troubleshooting, and legal compliance, then deleted or aggregated.

1.5 Subscriptions

If you purchase Remera Premium on iOS:

  • Apple processes payment, subscription management, and billing. We do not receive your Apple ID, payment card number, or billing address.
  • The iOS app sends a StoreKit 2 proof on AI requests: the signed transaction (X-App-Store-Signed-Transaction) and/or Apple’s original transaction id (X-App-Store-Original-Transaction-Id).
  • Our API verifies that proof with Apple’s App Store Server API. The client’s own Premium header is not trusted.
  • The API caches the result in Redis under remera:appstore:tx: plus Apple’s original transaction id. The cached fields are the tier (Premium or free), a reason code, the expiry time, the original transaction id, and the App Store environment (Sandbox or Production). The signed transaction itself is not stored. A second key may be a SHA-256 hash of the signed transaction, not the transaction text.
  • A Premium result is kept until the expiry Apple reported, and never longer than 24 hours. An inactive or failed check is kept for 5 minutes. If Redis is not configured, the same cache stays in process memory until restart.

The iOS app also reads StoreKit entitlements on the device to decide what to show. That on-device read does not replace the server check.

Android: Google Play Billing is not connected. The Android app does not send a Google purchase token, and the API does not verify Play purchases. Menu scanning stays unavailable on Android. We do not receive Google payment card details.

Manage or cancel an iOS subscription in your Apple ID settings.
